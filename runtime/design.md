# Runtime Module Design

## Executive Summary

The `runtime` module provides the foundational C infrastructure required by programs compiled with the Lyric compiler. It is a header-only library ([lyric_runtime.h](lyric_runtime.h)) that implements core language features such as dynamic slices, length-prefixed strings, optionals, error results, concurrency primitives (channels and spawning), and basic OS/File I/O abstractions. By providing these as C macros and inline functions, the runtime ensures that Lyric programs have a consistent and efficient execution environment while maintaining a small footprint and high performance through aggressive inlining. The runtime is designed to be "length-aware" throughout, allowing for binary-safe string operations and efficient slice manipulation without the overhead of null-termination for internal logic.

## File Inventory

- [lyric_runtime.h](lyric_runtime.h): The primary (and only) source file for the runtime. It contains all macro definitions, type declarations, and inline functions for slices, strings, optionals, results, channels, and OS interactions.

## Architecture and Data Flow

The `runtime` module is architected as a header-only C library, specifically designed to be included directly into the C code generated by the Lyric compiler. This design choice eliminates the need for a separate compiled library, simplifying the build process and enabling the C compiler (such as GCC or Clang) to perform aggressive inter-procedural optimizations and inlining tailored to the specific needs of the generated program.

The data flow within the runtime is centered around a set of core primitives that manage memory, strings, and concurrency. Memory management primarily relies on the standard C library's `malloc`, `realloc`, and `free` functions. Dynamic structures like slices and strings employ a doubling growth strategy to ensure amortized O(1) append operations. While the runtime maintains a hidden trailing null byte for many heap-allocated strings to facilitate interoperability with standard C library functions (like `fopen` or `stat`), its internal logic is strictly length-aware, relying on explicit length fields rather than null-termination.

Strings in Lyric are represented as length-prefixed byte slices, passed by value as small structs containing a pointer to the data, the current length, and the total capacity. This representation allows for O(1) length checks and O(1) sub-slicing without data duplication. Concurrency is implemented on top of POSIX threads (`pthreads`), with channels providing a synchronized communication mechanism using mutexes and condition variables. Error handling follows a result struct pattern, where a result contains a boolean error flag, a value for the success case, and a C-string error message, providing a robust and predictable way to manage failure states.

## Interface Implementations

The `runtime` module does not implement Lyric-level interfaces directly, as it is written in C and serves as the underlying substrate for the language. Instead, it defines the "C ABI" for Lyric's core types. The Lyric compiler's backend emits C code that directly utilizes the macros and types defined in this module. High-level Lyric data structures, such as `ArrayList` and `Dict` in the standard library, are built upon the slice and string primitives provided here.

## Public API

The public API of the `runtime` module is exported through a series of C macros and inline functions, categorized by the language features they support.

### Dynamic Slices
The runtime provides a generic-like slice system through the `LYRIC_SLICE_DEF` macro. This macro defines a specialized struct for a given element type, containing a data pointer, length, and capacity. A suite of manipulation macros allows for creating empty slices with `lyric_slice_empty` or initializing them from literals using `lyric_slice_lit`. The `lyric_push` macro handles element addition and automatic resizing, while `lyric_pop` removes the last element. Bulk operations are supported via `lyric_extend` for appending one slice to another and `lyric_slice_concat` for creating a new heap-allocated slice from two existing ones. Sub-slicing is performed with `lyric_subslice`, which creates a new view into the same underlying data. The `lyric_contains` macro provides a linear scan for element existence.

### Strings
The `lyric_string` type is a specialization of a byte slice and serves as the primary string representation. It is designed to be binary-safe and length-aware. Strings can be created from literals using `LYRIC_STR`, which marks them as non-owned static data, or from C strings and raw bytes using `lyric_str_from_cstr` and `lyric_str_from_bytes`, both of which perform heap allocations. The runtime provides a rich set of string operations, including equality checks with `lyric_str_eq`, lexicographic comparison with `lyric_str_cmp`, and concatenation with `lyric_str_concat`. Search operations include `lyric_str_contains`, `lyric_str_index_of`, `lyric_str_has_prefix`, and `lyric_str_has_suffix`. For more complex manipulations, the runtime offers `lyric_str_replace`, `lyric_str_repeat`, `lyric_str_join`, and `lyric_str_split`. Case conversion is handled by `lyric_toupper` and `lyric_tolower`, while `lyric_str_trim` removes whitespace. Formatting is provided by `lyric_sprintf`, which returns a heap-allocated string. For C interop, `lyric_new_error` converts a `lyric_string` to a null-terminated C string.

### Optionals and Results
To handle optional values and error states without null pointers or exceptions, the runtime provides `LYRIC_OPT_DEF` and `LYRIC_RESULT_DEF`. Optionals are created using `lyric_some` or `lyric_none`, and their presence is checked with `lyric_isnull`. Values are retrieved via `lyric_unwrap`, with `lyric_unwrap_checked` and `lyric_unwrap_class` providing safety checks that panic on null access. Results follow a similar pattern, with `lyric_ok` and `lyric_err` creating success or error states, and `lyric_is_err` checking the status.

### Channels and Concurrency
Concurrency is supported through a Go-like channel model and thread spawning. `LYRIC_CHAN_DEF` and `LYRIC_CHAN_IMPL` define and implement type-safe channels. Channels are created with `lyric_chan_make` and support blocking communication via `lyric_chan_send` and `lyric_chan_recv`, as well as non-blocking variants `lyric_chan_trysend` and `lyric_chan_tryrecv`. A channel can be closed with `lyric_chan_close`, and its resources freed with `lyric_chan_free`. The `lyric_spawn` function allows running a function in a new detached POSIX thread.

### Tagged Unions
The `LyricUnion` type provides a way to handle ad-hoc union types, such as `string | i32 | bool`. It uses an integer tag to identify the active member, supporting types like `int32_t`, `int64_t`, `float`, `double`, `bool`, `lyric_string`, and generic pointers. Constructors like `lyric_union_i32` and `lyric_union_string` simplify creation, and `lyric_union_fprint` allows printing the union's value to a file stream.

### OS and File I/O
The runtime wraps common system calls to provide a consistent interface for Lyric programs. File operations include `lyric_read_file` and `lyric_write_file`, which handle path null-termination internally. Directory listing is provided by `lyric_list_dir`, and file existence can be checked with `lyric_file_exists`. Path manipulation helpers include `lyric_path_dir`, `lyric_path_base`, and `lyric_path_ext`. The runtime also provides `lyric_getwd` for the current directory and `lyric_mkdtemp` for temporary directory creation.

### Conversions and Utilities
Basic type conversions are supported through `lyric_itoa`, `lyric_atoi`, and `lyric_parse_float`. The `lyric_char_to_string` function converts a single byte to a `lyric_string`. For output and error handling, `lyric_fprint_str` prints a string to a file stream, and `lyric_panic` prints an error message to stderr and terminates the program.

## Implementation Details

### Macro-Based Generics
The runtime heavily utilizes C macros to provide generic-like behavior for slices and channels. For example, `LYRIC_SLICE_DEF(int32_t, LyricSlice_int32_t)` creates a struct named `LyricSlice_int32_t`. This approach avoids the overhead of `void*` and provides better type safety at the C level. The `LYRIC_CHAN_IMPL` macro generates a set of functions specialized for a given type, allowing for efficient, type-safe communication without runtime type checks.

The `lyric_push` macro is particularly noteworthy. It checks if the current length has reached the capacity. If so, it doubles the capacity (starting at 4 if it was 0) and uses `realloc` to resize the buffer. A critical detail is how it handles static string literals: if the capacity is 0 but the length is greater than 0, it assumes the data points to a static literal and performs a `memcpy` into the newly allocated buffer instead of relying on `realloc` to copy the data.

### Length-Aware Strings and C Interop
String operations are designed to be "length-aware," meaning they do not rely on null-termination for their primary logic. This allows Lyric to handle binary data within strings seamlessly. However, for compatibility with C interop, heap-allocated strings often include a hidden trailing null byte (not included in the `len`), and functions that interface with the OS (like `fopen` or `stat`) perform temporary null-termination of path strings. This hybrid approach ensures that Lyric programs can easily call into C libraries while maintaining the flexibility of length-prefixed strings.

### Channel Synchronization
The channel implementation uses a circular buffer protected by a `pthread_mutex_t`. Two condition variables, `not_empty` and `not_full`, manage the blocking behavior. When a channel is full, producers wait on `not_full`; when it is empty, consumers wait on `not_empty`. When a channel is closed, `pthread_cond_broadcast` is used to wake up all waiting producers and consumers, who then check the `closed` flag and exit their wait loops. The `lyric_chan_trysend` and `lyric_chan_tryrecv` functions provide non-blocking alternatives that return immediately if the operation cannot be completed.

### Checked Unwrapping
To maintain safety in generated code, the runtime provides checked unwrapping macros. `lyric_unwrap_checked` and `lyric_unwrap_class` check the validity of an optional or pointer before access. If the check fails, they print a "panic" message to stderr and terminate the process. This behavior is the default for the Lyric compiler's C backend, though it can be bypassed in "unsafe" mode for maximum performance.

## Dependencies

The runtime depends on the following standard and system libraries:
- **Standard C Library**: `stdio.h`, `stdlib.h`, `stdint.h`, `stdbool.h`, `string.h`, `stdarg.h`, `ctype.h`.
- **POSIX Threads**: `pthread.h` (required for channels and `lyric_spawn`).
- **System Headers**: `unistd.h`, `dirent.h`, `sys/stat.h`.

## Technical Debt and Future Work

- **Memory Management**: Currently relies on standard `malloc`/`free`. Future iterations might explore slab allocation or more sophisticated memory tracking to improve performance and reduce fragmentation. A `#define LYRIC_SLAB_BLOCK 256` exists but is not yet fully utilized.
- **Embedded Nulls in Formatting**: The `lyric_sprintf` function uses `vsnprintf`, which does not handle embedded nulls in the format string. A custom length-aware formatter may be needed for full Lyric compatibility.
- **Error Message Flexibility**: Error messages in `lyric_err` are currently `const char*` literals. While efficient, this limits dynamic error message generation unless `lyric_new_error` is used to convert a `lyric_string` to a C-string.
- **Signal Handling**: The runtime currently lacks a unified signal handling mechanism, which would be beneficial for graceful shutdown and handling of asynchronous events.
